## Решения

1. **Hardhat 3 и покрытие.** Плагин `solidity-coverage` с Hardhat 3 не работает. В Hardhat 3 покрытие встроено: `hardhat test --coverage` (npm-скрипт `coverage`). Это и есть «`hardhat coverage`» из ТЗ.
2. **Node.js.** Hardhat 3 требует Node 22.10+, поэтому для разработки (компиляция, тесты, деплой) нужен Node 22+. Сам клиент (`client/`) использует только `ethers` и `node:crypto` и совместим с Node 18+.
3. **ESM.** Проект `"type": "module"` (требование Hardhat 3). Относительные импорты в TypeScript пишутся с расширением `.js`.
4. **`.env` без dotenv.** `.env` читается встроенным `process.loadEnvFile()` (Node 20.12+), без лишней зависимости. Hardhat 3 `configVariable(...)` берёт значения из `process.env` лениво, только когда сеть реально используется, поэтому тесты не требуют `.env`.
5. **Локальный компилятор `SOLC_PATH`.** В окружении разработки домен binaries.soliditylang.org заблокирован, поэтому Hardhat не может скачать solc. Добавлена опциональная переменная `SOLC_PATH` (путь к нативному solc 0.8.37, скачанному с GitHub-релиза). Если она пуста, Hardhat скачивает компилятор как обычно.
6. **Одинаковые настройки компилятора для профилей `default` и `production`.** `hardhat-verify` по умолчанию собирает профилем `production`, а `run` профилем `default`. Одинаковые настройки гарантируют совпадение байткода при верификации.
7. **evmVersion = `prague`.** Явно фиксируем EVM-версию, поддерживаемую Sepolia, Hoodi и локальной сетью, чтобы байткод не зависел от дефолта компилятора. Новые опкоды контракту не нужны. Оптимизатор включён, `runs = 200`.
8. **Белый список сетей деплоя:** Sepolia (11155111), Hoodi (560048), Hardhat local (31337). Всё остальное, включая mainnet (1), отклоняется.
9. **Скрипты управления запускаются через `tsx`, а не `hardhat run`.** `hardhat run` в Hardhat 3 не принимает позиционные аргументы, а скриптам нужны значения (`set-string "..."`). Скрипты используют саму клиентскую библиотеку (`client/`), сеть задаётся флагом `--network <name>` (по умолчанию `sepolia`), адрес контракта берётся из `deployments/<network>.json`.
10. **Пуш.** ТЗ запрещает пуш в удалённый репозиторий. Работа ведётся в облачной сессии, контейнер которой временный, поэтому итоговые коммиты пушатся только в рабочую ветку `claude/valuestore-contract-client-9n3n59` (не в `main`, без PR), чтобы не потерять результат. Репозиторий уже был инициализирован (`git init` не нужен).

## Контракт (этап 2)

11. **Единая ошибка прав.** `_checkOwner()` из `Ownable` переопределён и бросает `NotAuthorized(caller)` вместо `OwnableUnauthorizedAccount`. Так редактор, пытающийся добавить редактора или передать владение, получает `NotAuthorized`, как требует раздел 12 ТЗ.
12. **Нулевой адрес владельца → `ZeroAddress`.** И в конструкторе (проверка в аргументе базового конструктора `Ownable`), и в `transferOwnership` вместо `OwnableInvalidOwner`.
13. **`addEditor(owner)` → `AlreadyEditor(owner)`.** Владелец уже неявный редактор. Если бы его можно было внести в список, после передачи владения старый владелец сохранил бы права через список, что противоречит «старый владелец теряет права».
14. **Редакторы сохраняются при передаче владения.** ТЗ не требует сбрасывать список. Новый владелец может снять ненужных редакторов сам.
15. **`clear*` для незаданного значения не падает.** Отдельной ошибки в ТЗ нет. Сброс идемпотентен, но всё равно эмитит событие и увеличивает `revision` (правило «revision растёт на каждый сброс»).
16. **Порядок проверок в `set*`: сначала права, потом режим, потом длина.** Посторонний всегда получает `NotAuthorized` и ничего не узнаёт о режиме из ошибки. Режим и так публичен через `mode()`, это просто последовательность.
17. **Контракт не проверяет формат шифротекста** (версию, длину IV/тега). Это забота клиента, контракт хранит только непрозрачные байты в пределах лимита.
18. **Покрытие ветвей.** Встроенное покрытие Hardhat 3 (EDR) считает строки и выражения, но не ветви, а `solidity-coverage` с Hardhat 3 несовместим. Скрипт `scripts/check-coverage.ts` проверяет порог 95% по строкам. Для ветвей: каждый `if (...) revert` покрыт тестом и с выполнением `revert`, и с успешным путём (тесты негативных и позитивных сценариев), то есть фактически обе ветви каждого условия пройдены.
19. **Предупреждения компилятора** `"at" will be promoted to keyword` идут из `EnumerableSet.sol` OpenZeppelin 5.6.1 при компиляции solc 0.8.37. Код OpenZeppelin не меняем. В `ValueStore.sol` предупреждений нет.

## Деплой (этап 3)

20. **Логика деплоя вынесена в `scripts/lib/`** (`networks.ts`, `deploy-config.ts`, `deployments.ts`, `deploy-core.ts`), а `scripts/deploy.ts` только связывает их с Hardhat. Так белый список, разбор `.env` и запись `deployments/*.json` покрыты тестами без сети.
21. **Подтверждения:** `CONFIRMATIONS` из `.env` (по умолчанию 2) для Sepolia/Hoodi, 1 для локальной сети.
22. **Ошибка верификации не роняет деплой.** Контракт уже задеплоен и сохранён, поэтому при сбое Etherscan скрипт печатает готовую команду `npx hardhat verify ...` для повтора.
23. **Запуск без `--network`** деплоит во временную in-process сеть Hardhat (имя сети `default`, файл `deployments/default.json`). Для локального сценария со скриптами управления нужна `npm run node` + `npm run deploy:local` (сеть `localhost`).

## Клиент (этап 4)

24. **Собственный минимальный ABI** (`client/abi.ts`, human-readable). Клиент не зависит от артефактов Hardhat и может копироваться во внешнее приложение вместе с `ethers`.
25. **`connect()` синхронный**, как в примере ТЗ. Режим (`mode()`) и chainId читаются лениво при первом обращении и кэшируются (оба неизменны). При сетевой ошибке кэш сбрасывается.
26. **Помимо `rpcUrl` можно передать готовый `provider`** (используется в тестах с in-process сетью Hardhat и в приложениях со своим провайдером).
27. **Кэш ethers отключён** (`cacheTimeout: -1`) для провайдера, который клиент создаёт по `rpcUrl`. Иначе две записи подряд в пределах 250 мс получали устаревший nonce (найдено сквозным тестом).
28. **Согласованное чтение.** `getString`/`getNumber` читают `has*` и значение двумя `eth_call`. Между ними может пройти запись, поэтому чтение обрамляется чтением `revision` до и после и повторяется (до 3 раз), если `revision` изменилась.
29. **В private-режиме без ключа** `getString`/`getNumber` бросают `KeyRequired` всегда, даже если значение не задано. `hasString`/`hasNumber`/`getRevision`/`getEditors` ключа не требуют: это публичные метаданные.
30. **Проверки до отправки транзакции** (`InvalidValueError`): пустая строка, строка > 1024 байт (public), шифротекст > 2048 байт (private, то есть строка > 2019 байт), число вне `uint256`, некорректный адрес. Экономит газ и даёт понятную ошибку.
31. **Ошибки контракта** декодируются в `ContractRevertError { errorName, errorArgs }` по ABI. Revert-данные ищутся во вложенных полях ошибки, потому что ethers и Hardhat упаковывают их по-разному.
32. **Дополнительные типизированные ошибки:** базовая `ValueStoreError`, `InvalidKeyError` (ключ не 32 байта), `InvalidValueError`, `ContractRevertError`. Требуемые ТЗ `KeyRequired` и `DecryptionError` названы ровно так.
33. **Расшифрованное число проверяется**: каноническая десятичная запись без ведущих нулей и не больше `2^256 - 1`, иначе `DecryptionError`. Невалидный UTF-8 в строке тоже даёт `DecryptionError`.
34. **Writer наследует Reader**, поэтому через writer можно и читать. Методы записи ждут включения транзакции в блок и возвращают receipt.
